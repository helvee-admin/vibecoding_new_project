# 测试与发布的工作规范

这两个领域分别回答“行为是否符合预期”和“这个版本是否适合交付”。生成项目时把对应部分写入各自的领域规则。

## 测试

- 从用户最重要的结果选一条主要路径和最可能造成损失的异常。原型评审可观察用户能否独立完成任务。已有可运行版本时，记录前提、操作、预期、实际、环境和证据位置。选择与本次变更相关的平台、数据和辅助操作方式。
- 对异步交互同时检查屏幕反馈与持久结果。例如模拟提交中断后再试，验证输入保留、结果可确认、实际只新增一条记录。看不到后台结果时标明该项待验证。
- 缺陷按用户影响、频率、是否可恢复和是否有绕行方法说明严重度。交给工程时附版本、最短复现步骤、样本和观察到的结果。预期行为本身不明确时先找产品或设计。修复验证包含原失败路径和与之直接相关的既有行为。
- 输出通过、失败、受阻或尚未验证的判定及证据。临近发布时，把影响交付的缺陷与剩余风险交给发布领域，避免用测试用例数量替代用户任务的结果。

## 发布

- 先区分内部试用、定向邀请和面向公众。一次试用通常只需明确版本、接收人、最短使用说明、已知限制和反馈入口。
- 准备正式交付时，核对实际提供的功能、目标平台或地区、质量证据、用户可见说明、相关隐私声明与素材授权。对审核、分发或部署有差异的平台分别核实。将可对外说明的能力和生效时间交给市场推广。
- 给出可以交付、应暂缓或范围应缩小的建议和依据。对已有用户的变更，指定谁观察哪个异常、何时暂停以及可行的恢复方式。高影响数据变更要说明旧版本能否继续使用数据。
- 交付清单记明对象、版本、授权、实际交付状态和验证结果。对外发布由有权限且已获授权的人执行。获客策略与内容表现由市场推广负责，承诺范围有争议时回产品确认。
