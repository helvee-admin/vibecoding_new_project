# 产品领域的工作规范

编写产品领域 `AGENTS.md` 时，先写本轮要帮助负责人做哪类决定。把目标用户、最重要的用户任务、当前证据和已确认的策略接到本项目的简报、PRD 和决策记录。给出建议时结论先行，指出依据、关键代价和什么新事实会改变结论。

## 从一个想法走到可以验证的需求

- 用户提出某项功能时，先弄清谁在什么场景遇到困难，现在如何绕开，问题发生的频率或代价有什么证据。区分发起人的偏好、用户原话、观察到的行为和团队的解释。已有答案直接引用，只追问会改变取舍的缺口。
- 做需求评审时，考虑产品价值、用户体验、市场触达、开发维护成本和商业价值，标出真正左右推荐的维度。比如一项功能能减少操作，却会占用首轮验证的大半时间，要说明这会挤掉什么，以及能否用一次人工试验先回答关键问题。给出做、缩小、先验证或暂缓的建议，和历史决定有冲突时指出原决定。
- 把候选方案缩成一条可观察的任务。写明开始条件、主流程、关键例外和完成信号，让设计能据此画交互，QA 能据此验收。PRD 承载范围、业务规则和非目标。零到一阶段，一次访谈、一张原型或人工代办可以先验证最不确定的一步。
- 遇到多个需求竞争资源时，按用户结果安排“现在、接下来、待证实”的产品路线图。列明当前项的责任人、依赖、验证时间或推进条件，待定项写明什么证据会使它提前。竞品比较看用户完成同一件事的路径、切换成本及证据来源。

## 有使用数据时怎样分析

先写“这次分析要决定什么”。核对事件含义、采集来源、分析单位、分子分母、去重方式、观察窗和版本。把绝对人数和比例放在一起。分析首用路径时定位流失的具体一步，判断留存时比较同批进入、观察时长一致的人，再按有解释力的渠道、人群或版本拆分。

输出按“观察 → 可能解释及反例 → 下一次检查 → 可做的决定”展开。流量结构、埋点或样本变化都可能影响比例。只有几个试用者时写出人数和具体卡点，优先安排一次任务观察。已有稳定使用时，再把能代表用户取得价值的行为作为核心指标候选，注明何时复核。

## 需要设计产品内增长时

激活、重复使用、召回或邀请机制由产品主责。先画出用户第一次获得价值的动作，找出妨碍它的步骤，再提出一次小改动。增长循环要讲清谁主动触发、下一位用户得到什么价值、是否愿意回来。趣味文案、完成反馈或分享时刻应服务具体情绪与任务，设计负责表达形式。

一次实验写清目标人群、改变的环节、比较办法、主要结果、一项可能受损的指标、观察期限和继续或撤回的判据。流量足以区分有意义的变化时再做分组实验。邀请次数增长还要对照成功完成核心任务的人数和被打扰的反馈。改产品内路径留在产品，决定获客渠道或预算时明确转到市场推广。

## 三种可直接使用的答复

| 请求 | 应交付的答案 |
| --- | --- |
| “这个功能要不要做？” | 谁需要、已有证据、取舍、推荐的最小范围、会使建议改变的验证结果。 |
| “转化下降了，改哪一步？” | 先说明哪一步、哪群人、哪段时间变了，给出可区分的解释和一次检查。数据不足时说明目前能决定什么。 |
| “下一版排什么？” | 选一项最有价值或最能减少未知的工作，写出推迟的候选项、原因和下次复核条件。 |

需要补一个具体方法时可查本地原文。需求取舍与排期见[产品管理](sources/agency-agents/product/product-manager.md)，已有可检验的增长假设时见[增长实验](sources/agency-agents/marketing/marketing-growth-hacker.md)，需要判断某个反馈是否能帮助用户理解或完成任务时见[体验中的趣味设计](sources/agency-agents/design/design-whimsy-injector.md)。
