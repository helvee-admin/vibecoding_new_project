# 工程领域的工作规范

工程对已确认体验的实现负责。开始前读当前需求、适用的交互说明、数据与权限约束。把用户操作转成能检验的行为，再选择对现有架构影响最小的实现。原型阶段先让一条路径跑通，技术选择说明它解决哪个具体问题。

## 把交互说明变成运行行为

- 约定输入、系统反馈、状态由谁保存、何时算成功。检查正常路径中最可能打断用户的一步，例如快速连点、网络超时、操作取消、离开再返回。耗时操作应及时给出进度或等待反馈，并提供与真实结果一致的恢复方式。
- 对会产生订单、预约等持久结果的操作，界面和服务端的状态要能对账。用户重复点击或请求已经成功但回包丢失时，按同一笔操作查询或安全重试，保留可恢复的输入。交付证据要同时显示用户看到的反馈和实际生成了几笔记录。
- 复用项目的组件、导航、数据层和平台惯例。保持系统返回、键盘焦点、读屏标签、动效偏好和手势替代操作符合交互约定。移动端有需要时验证前后台切换、弱网和代表性真机。网页对应验证浏览器返回、键盘和显示尺寸。按实际环境选择。
- 性能从可感知的问题入手，如点按后迟迟无反馈、列表卡顿、启动慢。在目标设备或浏览器用同一任务记录基线、调整和复测条件。观测指标或性能目标以用户感受到的延迟和项目证据为依据。

## 实现取舍与交付

把界面状态、业务规则、存储和外部调用的职责分清。新能力用到账号、数据、分析事件或第三方服务时，核对已确认的用途、最小权限、失败处理和历史数据兼容。已有数据或高影响操作才需要针对性检查迁移、重试或回退。

交付时说明用户现在能做什么、在哪个版本和环境验证、尚有哪些差异。工程发现交互定义无法实现或不同做法会改变用户体验时，把具体限制和可行选项带回设计。改变产品承诺时进入产品领域，修复后的复现步骤交给 QA。

涉及移动端生命周期、设备约束或平台交互，且需要补充实现思路时，可查[移动应用开发原文](sources/agency-agents/engineering/engineering-mobile-app-builder.md)的相应小节。框架选择与性能预算取决于目标项目和实测结果。
