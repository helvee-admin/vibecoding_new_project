# 领域职责与工作准则

用于起草相应领域的 `AGENTS.md` 和当前规范。一个人可以承担多个领域，职责和验收依据仍按任务区分。只创建需要独立维护的领域。

需要具体做法时，按手头的决定选读[产品](product.md)、[设计](design.md)、[工程](engineering.md)、[质量与发布](quality-and-release.md)或[市场推广](marketing.md)的对应小节。领域指南末尾收录了可选原文，查阅条件见[Skill 主文件](../SKILL.md#什么时候查第三方原文)。

## 产品

规范可用 `PRD.md`。先说明目标用户、任务、价值和已有依据。提出候选功能时记录关键路径、非目标、可观察的成功标准和最小验证。对比用户收益、业务价值、实现与维护成本。把用户偏好、验证结果和确认后的范围分别写清楚。

## 设计

规范可用 `design-system.md`，复杂流程按需另设。以任务和交互为主线，记录可复用的设计变量、组件及行为。根据风险覆盖正常、空、加载、失败、取消、权限与无障碍状态。记清资产来源、许可和交接规格。区分设计已经确定、已经实现与已经验收。

## 工程

规范可用 `architecture.md` 和 `development-principles.md`，数据与权限有独立复杂度时另记。实现前简要说明改动和验证方式，按行为、调用方、契约和数据来界定影响。

- 优先复用已有职责。仅为实际需要增加依赖、抽象、缓存、预热、重试或恢复机制，以复现、测量、平台契约或明确数据流说明必要性和代价。
- 在外部输入边界校验并转成明确的内部类型，避免反复解析或校验同一内容。在真正提交、写入或执行副作用时，仍处理可能变化的权限、资源和业务状态。
- 让主流程易读。抽象应表达真实职责、明确复杂逻辑或提供实际复用。注释解释原因、约束和反直觉行为。修改生成文件的源头，再重生成受影响产物。
- 先测量实际瓶颈，避免昂贵工作阻塞主流程。改动触及持久化、权限或迁移时，同步考虑旧数据、失败后的状态、重试及回滚。
- 测试生产逻辑的可观察行为。按影响选编译、单元、集成或正常入口验证。外部服务可用必要替身，记录与真实环境的差别。先解释失败再修复，按最新实际通过的版本汇报验证，保留仍有用的回归。

## 质量验收（QA）

规范可用 `acceptance-checklist.md`。从已确认需求或缺陷建立用例。用例写明前置条件、操作、预期、实际结果、版本和环境。依据影响覆盖边界、失败、取消、权限和数据保护。开发自测和正式验收分别记账，区分未执行、通过、失败、受阻、不适用和经授权免验。结果引用准确的提交、构建或证据摘要，合成样本、模拟环境及生产或真机结果分别说明。

## 发布

规范可用 `release-checklist.md`。先核对目标环境、候选身份、验收判定和发布权限，再核对用户文案、功能行为、配置、隐私与许可。区分准备、上传、提交审核、发布和上线验证。按批准的步骤推进并读回实际结果。出错时先保留可核验的状态，按项目的回退或修正方案处理。完成后在版本收尾记录中链接实际发布物、源码基线和下一步。各环境和平台的发布授权及结果分别管理。

## 营销与增长

有渠道运营、传播、用户获取、增长实验或数据复盘职责时，可增加 `marketing`。规范可用 `growth-playbook.md`，渠道、内容和实验按需落文档。

- 把受众和渠道选择作为待验证假设。内容承诺对照当前产品和已授权素材。按实际进展区分研究、稿件、排期、发布与复盘。
- 先写实验问题和衡量口径。记录来源、版本、窗口、分母、基线和局限。数据不足时写清能得出的结论，观察到的关联不写成因果。
- 把用户反馈整理成现象、证据、可能原因及建议验证。按项目约定交给产品或其他归属领域，范围调整由相应决策人确认。公开发布、联系外部对象、投放支出和账号修改按实际授权处理。
