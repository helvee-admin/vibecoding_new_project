# 文件与决策记录蓝图

下面的路径相对目标项目根目录。优先复用项目已有的同职责文件。生成后把实际路径写入路由，领域工作规则和适用的操作说明都保存在目标项目里。

需要核对空项目的目录示意和首次填写字段时，可查[初始化与目录骨架](intake-and-layout.md)。需要区分领域责任、开发自测与正式验收时，可查[领域职责](domain-playbooks.md)中的对应小节。

## 根规则与治理层

| 位置 | 写入内容 |
| --- | --- |
| `AGENTS.md` | 项目目标与当前边界、事实与判断的区别、执行或评审的处理方式、确认门槛、工具选择、领域路由和跨域交接规则。路由每行说明“什么决定 → 主责领域 → 处理它的最短阅读路径”，历史决定或数据按问题补读。 |
| `docs/README.md` | 新协作者从哪里开始、资料分别在哪里。用项目内相对链接指向实际文件。 |
| `docs/governance/current-brief.md` | 当前阶段及依据、已确认事实、关键约束、活跃领域、仍未知的事项、最近要做的决定。随事实变动更新。 |
| `docs/governance/decision-log.md` | 跨域决定的唯一完整记录。记录编号、日期、主责与受影响领域、已确认决定、取舍原因、关联资料和状态。改判时关联原编号，保留当时的理由。 |
| `docs/governance/chatgpt-local-project-startup.md` | 需要跨对话协作时生成。让能访问项目文件的新对话从根规则和治理资料开始，按根路由读取领域规则。 |

## 每个启用领域的文件

`docs/<领域>/AGENTS.md` 写明这类讨论要解决的决定、应读的项目内资料、这个阶段实际采用的工作方法、验收或判断依据、结论归档位置和跨域交接。把对应参考材料中适用的步骤改写成项目可执行的提示词。例如产品侧只有试用笔记时，明确要求描述用户在哪一步卡住、尝试了什么，并给出下一次验证办法。

生成的根路由、领域 `AGENTS.md` 和新会话启动说明只列目标项目自身的必读资料。第三方角色原文留在 Skill 档案中。确有采用的方法，用项目自己的语言写清适用条件。引用来源时可在相应决定中注明原文的文件名和版本，避免把档案目录或角色模板复制为后续会话的指令。

**只有一个短期验证时，每个活跃领域先保留自己的 `AGENTS.md` 和手头真正要用的材料。** 当前进展可以在治理简报按领域各写一行。待某个领域需要单独持续更新时，再建该领域的 `current-brief.md`。事实观察标记来源、日期和适用范围，原始反馈留在访谈或实验材料中。

每个领域保留独立的决策归属。第一次确认本领域独有的取舍时，创建或更新该域的 `decision-log.md`。仅需知道一条全局决定时，在现有工作材料引用全局编号即可。沿用已有日志或项目明确要求预置的日志。每次新增独立资料时，补上根路由和索引中的真实入口。

| 领域 | 承载当前有效规范的建议位置 | 初期可用的一小段内容 |
| --- | --- | --- |
| 产品 | `docs/product/PRD.md` | 用户问题、候选核心路径、范围、验证判据。 |
| 设计 | `docs/design/design-system.md` | 本轮任务的入口、动作、反馈、恢复方式及少量可复用样式。 |
| 工程 | `docs/engineering/architecture.md` | 目标环境、关键状态和数据归属、实现边界、验证方式。涉及用户数据时在此处或项目已有权限文档说明用途和生命周期。 |
| 测试 | `docs/qa/acceptance-checklist.md` | 可运行的一条主要验收与最重要的异常，还缺什么证据。 |
| 发布 | `docs/release/release-checklist.md` | 本次交付对象、版本、可用性检查、停止或恢复办法。 |
| 市场推广 | `docs/marketing/marketing-plan.md` | 目标人群、接触途径、待检验的表达、期望行为、反馈方式。 |

早期在现有规范内用小节承载相关工作。出现独立维护需求时再拆出路线图、交互说明、指标字典或活动复盘，更新索引与路由。生成的文档只列真实存在的必读项。

## 可写入领域 AGENTS.md 的交接规则

当下一项决定属于另一领域或在那里讨论更有效时，先向用户点名建议进入的领域，并给出理由、实际入口和要带过去的问题。一项工作涉及多方时，说明谁做决定、谁提供证据、什么结果回来后可继续。用户要另开对话时，可直接复制如下交接语式。

> 这部分建议进入【目标领域】对话，因为接下来要决定……。已知……，依据在……，还缺……。请在……处继续，得出……后回到【原领域】处理……。

同一个主题可能产生不同交付。是否在产品内引入邀请机制归产品，邀请被拒后如何继续归设计，重复点击时只发送一次归工程，验证重复发送是否已修复归 QA，渠道宣传文案归市场推广。话题回到已授权的原任务时，接着完成即可。
