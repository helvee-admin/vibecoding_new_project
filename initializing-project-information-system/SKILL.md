# 建立项目信息系统

让下一位协作者读少量资料就能知道当前目标、有效规则、代码或资产入口，以及下一步由谁完成。以本项目的事实和用户决定为准。历史项目、附件和角色提示词只作为参考，除非用户明确采用其中的规则。一次性开发任务沿用项目已有规则。

## 识别任务与搭建范围

1. 确认真正的目标目录。先读已有根级和相关路径的规则、资料入口、代码布局及工作区状态。已有系统优先沿用，保留用户文件与并行工作。仅讨论或诊断时给出对齐摘要，不创建文件。
2. 区分可核实事实及来源、用户已确认决定、待定项、临时假设和建议。用户提出的功能或方案可作为候选，先弄清它要解决的问题。资料有冲突时说明具体影响，沿用仍有效的已确认口径，必要时请决策人澄清。
3. 选择当前有明确职责的领域。缺失信息会改变项目范围、文件归属或实施结果时，集中问最少的问题。用户已要求直接搭建且不确定项可留空时，创建足以继续工作的最小骨架，将未知写成待定。
4. 按 [初始化与目录骨架](references/intake-and-layout.md) 创建或补齐入口。给实际启用的领域写任务路由、更新规则及已经知道的内容。涉及领域准则时读 [领域职责](references/domain-playbooks.md) 的对应章节。新增会话、平台、领域或做版本收尾时读 [协作与维护](references/ongoing-collaboration.md) 的对应章节。

## 运行规则

- 根 `AGENTS.md` 保存稳定的目标、协作规则、授权边界与路由，`docs/README.md` 负责导航。简报只反映现行状态，更新时替换过期条目。稳定的需求和约束写入对应规范。测试日志、讨论和生成物按需要单独存放。
- 全局约束和跨领域决定在治理层有一个权威正文，单领域决定在归属领域记录。给已确认决定分配稳定编号。其他领域只链接编号并说明实施影响。未知、假设、实测结果和待确认建议可以写进简报或独立记录，不能冒充已确认决定。
- 新会话读根规则、治理简报、当前领域入口与当前任务引用的规范或决定。按实际需要继续读取，避免把历史记录传给每个会话。交接写清范围、输入、完成与未完成事项、验证级别、下一步和归属。
- 已授权的工作直接推进。方案评估和范围内实施按用户要求进行。遇到会实质改变已确认目标、接口、数据、权限、成本或外部承诺的选择，只让用户决定那个选择。搭建资料不授予推送、发布、支出、删除用户数据或外部改动的权限。
- 开发验证、正式验收和实际发布各自记录。先定义什么算完成，再按本次影响验证并说明证据边界。清理过程材料时保留可构建源码、现行结论、在用回归所需的最小夹具和正式发布材料。

## 交付检查

确认链接对应真实文件，根规则与领域规则一致，临时假设有标记，启用领域或平台有明确读写范围。核对文档只含目标项目已授权的信息。汇报本次创建或更新的入口、影响后续工作的待定项，以及下一步。
